## 二、核心模块

### 2.1 分块器（chunker.py）

**策略**：表格保护 + 句子边界分块 + 重叠

- 表格整块保留，不切断
- 正文按句子边界分块（max_chars=600）
- 相邻块重叠 50 字符（按句子边界截断）
- chunk_id 带文档哈希前缀，避免多文档冲突

**chunk_id 生成规则**：
```
文档哈希(4位) + _ + 类型(p/c) + 序号
例：a3b1_c0000, f7c2_p0012
```

### 2.2 向量存储（vector_store.py）

**多文档支持**：
- 每条记录带 `source_file` 字段标识来源文档
- 插入时通过 `content_hash` 去重
- 查询时支持 `source_filter` 按文档过滤

**关键方法**：
- `insert(chunks, vectors, source_file)` — 插入并去重
- `search(query_vector, top_k, source_filter)` — 向量检索
- `query_by_source(source_file)` — 查询文档是否已入库
- `delete_by_source(source_file)` — 删除指定文档数据

### 2.3 检索器（retriever.py）

**RRF 融合**：
```python
RRF_K = 60
DENSE_WEIGHT = 1.0    # 向量检索权重
SPARSE_WEIGHT = 1.5   # BM25 权重更高（关键词匹配对精确问答更重要）
```

**流程**：
1. 向量检索（top_k * 3 候选）
2. BM25 检索（top_k * 4 候选）
3. RRF 融合（加权）
4. 按 rrf_score 降序排列
5. 返回 top_k 结果

### 2.4 LLM 生成器（generator.py）

**多文档 Prompt 规则**：
- 只用参考资料里的信息回答
- 优先使用原文措辞
- 不同文档涉及不同公司，注意区分，不要张冠李戴
- 回答时说明信息来自哪份文档

**上下文格式**：
```
【资料1·来源：招股说明书2】第五节 发行人基本情况
公司名称：武汉力源信息技术股份有限公司...

【资料2·来源：招股说明书2】第十一节 募集资金运用
本次募集资金拟投资以下项目...
```

### 2.5 组件初始化（components.py）

**启动流程**：
1. 加载 Embedding、Milvus、Reranker 等基础组件
2. 加载分块缓存（`storage/chunks_cache.pkl`）
3. 遍历 `data/*_refined.md`，逐个检查是否已在 Milvus 中
4. 新文档：分块 → 编码 → 插入 Milvus
5. 已有文档：跳过索引，只加载分块（用于 BM25）
6. 构建 BM25 索引

## 三、遇到的问题和解决方案

### 3.1 chunk_id 冲突导致数据覆盖

**问题**：两个文档的 chunk_id 都是 `c0000, c0001...`，Milvus 用 chunk_id 做主键，后入库的文档覆盖了前一个的数据。

**原因**：Chunker 使用全局递增序号生成 chunk_id，不同文档从 0 开始。

**解决**：chunk_id 加文档名哈希前缀（如 `a3b1_c0000`），每个文档生成唯一 ID。

### 3.2 前端不显示回答内容

**问题**：API 返回了正确的 JSON 响应，但前端只显示响应时间，不显示内容。

**原因**：前端 SSE 解析期望 `{"type": "token", "data": "xxx"}` 格式，但后端发送的是 `{"token": "xxx"}` 格式，字段名不匹配。

**解决**：修改后端 SSE 输出格式，与前端期望一致：
```python
yield f'data: {{"type": "token", "data": "{token}"}}'
yield f'data: {{"type": "sources", "data": [...]}}'
yield f'data: {{"type": "query_analysis", "data": {{...}}}}'
yield f'data: {{"type": "done"}}'
```

### 3.3 .env 文件编码错误

**问题**：启动时报 `UnicodeDecodeError: 'utf-8' codec can't decode byte`。

**原因**：PowerShell 的 `Set-Content` 默认使用系统编码（GBK），写入 .env 后 Python 的 `load_dotenv` 用 UTF-8 读取失败。

**解决**：用 `[System.IO.File]::WriteAllText()` 强制 UTF-8 编码写入。

### 3.4 sentence-transformers 版本不兼容

**问题**：加载 Embedding 模型时报 `NotImplementedError: Cannot copy out of meta tensor`。

**原因**：sentence-transformers 3.3.1 与 PyTorch 2.5 的 meta tensor 机制不兼容。

**解决**：降级到 sentence-transformers 2.7.0。

### 3.5 端口清理超时

**问题**：`start.bat` 启动时报端口 8007 被占用，清理超时后启动失败。

**原因**：加载了 CUDA 模型的 Python 进程释放显存需要较长时间，`taskkill /F` 后 5 秒端口还没释放。

**解决**：
1. `start.bat` 启动前先 `taskkill /F /IM python.exe` 杀掉所有 Python 进程
2. 循环检测端口是否释放（不再硬等固定秒数）
3. `run.py` 中等待时间从 5 秒增加到 20 秒

### 3.6 检索精度低（找不到正确答案）

**问题**：用户问"募集资金拟投资哪些项目"，系统返回泛泛的公司介绍页，而不是包含具体项目的页面。

**原因**：
1. 向量检索返回语义相似但内容不精确的结果
2. RRF 融合时 BM25 权重太低，关键词匹配结果被稀释
3. top_k 太小（5），正确答案在第 6-10 位被截断

**解决**：
1. BM25 权重从 1.0 提升到 1.5
2. 内部检索数量增大到 top_k * 3（最少 10 条）
3. Rerank 候选池从 12 扩大到 16

### 3.7 响应时间超 3 秒

**问题**：复杂查询响应时间 5-8 秒，远超 3 秒要求。

**原因**：Query Understanding 调用 LLM 做意图分析，额外增加 2-3 秒。

**解决**：
1. 砍掉 Query Understanding，改用纯规则判断意图（0 秒）
2. 跳过 Rerank（省 0.3 秒）
3. 问候语不调 LLM，直接返回固定回答
4. 减少 LLM max_tokens（1000 → 800）

**优化后耗时分布**：
- 问候语：< 0.1 秒
- 简单查询：2-3 秒（Embedding 0.5s + LLM 1.5-2s）
- 复杂查询：3-6 秒（取决于 DeepSeek API 负载）

### 3.8 启动时重复解析文档

**问题**：每次启动都要重新分块和编码文档，浪费时间。

**原因**：分块结果没有缓存，每次启动都从头开始。

**解决**：
1. 分块结果缓存到 `storage/chunks_cache.pkl`
2. 启动时先检查 Milvus 中是否已有文档数据
3. 已有的跳过编码，只加载分块用于 BM25

## 3.9 多轮对话

**目标**：支持上下文追问，让 LLM 记住对话历史。

**方案**：Redis 短期记忆 + LLM 上下文注入。

**存储**：
- Redis List：`chat:{chat_id}:history`
- 每条记录：`{"role": "user/assistant", "content": "..."}`
- 最多保留 10 轮（20 条消息），TTL 1 小时
- 删除对话时自动清空 Redis 数据

**流程**：
1. 前端发送请求时带上 `chat_id`
2. 后端从 Redis 读取该对话的最近历史
3. 历史消息插入 system prompt 和当前问题之间，传给 LLM
4. LLM 生成回答后，本轮 Q&A 存回 Redis

**LLM Prompt 设计**：
- System prompt 明确告知 LLM 有两部分信息：对话历史 + 文档参考资料
- 对话历史中的用户个人信息与文档资料同等重要
- 规则优先级：用户个人信息 > 文档资料 > 模型常识

**适用场景**：
- 追问（"那第二家呢？"、"它的注册资本呢？"）
- 个人信息记忆（"我叫李达" -> "我是谁？"）
- 上下文补充（"再详细说说"、"举个例子"）

**局限**：
- 依赖 Redis，Redis 不可用时降级为无历史模式（不影响基本问答）
- 历史窗口 10 轮，超过 10 轮的早期对话会被丢弃
- 不做 query rewrite，指代消解依赖 LLM 自身能力
