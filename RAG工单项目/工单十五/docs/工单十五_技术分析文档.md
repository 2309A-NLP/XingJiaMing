## 2. 基准测试（优化前）

### 2.1 测试环境
- **RAGFlow版本**：v0.26+（Docker CPU版）
- **Embedding模型**：BGE-M3（SiliconFlow）
- **Rerank模型**：SiliconFlow Rerank
- **LLM**：mimo-v2.5-pro（纯文本版）
- **分块方法**：Paper模式（自动识别论文结构）

### 2.2 基准结果
| 编号 | 回答 | 结果 | 失败原因 |
|------|------|------|----------|
| Q1 | 至少部分预还原的铁矿石 | ✅ | - |
| Q2 | 栓钉、链条 | ✅ | - |
| Q3 | 无法确定 | ❌ | 图片信息未提取 |
| Q4 | 无法确定 | ❌ | 图片信息未提取 |
| Q5 | 部件10（落料架） | ❌ | 检索到错误chunk |
| Q6 | 无法确定 | ❌ | 图片信息未提取 |

**基准准确率：2/6 = 33%**

### 2.3 问题根因分析

#### 2.3.1 RAGFlow检索流程
```
用户问题 → 向量检索（BGE-M3）→ Rerank重排 → Top-K chunks → LLM生成答案
```

#### 2.3.2 失败原因
1. **OCR提取不完整**
   - RAGFlow的OCR只能提取文字，无法理解图片内容
   - 技术图纸中的部件编号、位置关系、连接方式等信息丢失

2. **向量检索的局限性**
   - BGE-M3对"部件13相对于部件12的位置"这类查询，无法匹配到图片chunk
   - 图片chunk的向量表示缺乏语义信息

3. **Rerank无法弥补**
   - 即使提高top_n，图片相关chunk也排不进前20
   - Rerank依赖文本相似度，对图片内容无能为力

## 4. 优化过程中的问题与解决

### 4.1 问题1：Q5回答错误（部件10 vs 部件13）

**现象**：
- 初版chunk注入后，Q5仍然回答"部件10"
- 检索结果显示"散料通过部件14导入落料架10"

**原因分析**：
- chunk中"散料通过部件14导入落料架10"的表述误导了LLM
- LLM将"导入"理解为"下一步经过"

**解决方案**：
```python
# 修改chunk内容，明确流动路径
"散料从部件14（输入管）进入后，下一步会经过部件13（链条）进行分散。"
```

**验证**：
- 更新chunk后，Q5正确回答"部件13"

### 4.2 问题2：Chunk更新后检索延迟

**现象**：
- 更新chunk内容后，立即测试仍返回旧结果

**原因分析**：
- Elasticsearch索引有刷新延迟

**解决方案**：
```python
# 强制刷新索引
es.indices.refresh(index='ragflow_21ed0cb865a111f1888b6b9abc90b74f')
```

### 4.3 问题3：多模态模型参数错误

**现象**：
- 使用mimo-v2.5（多模态）时，RAGFlow自动传images参数导致API报错

**原因分析**：
- RAGFlow检测到多模态模型，自动附加图片参数
- MiMo API不支持此参数格式

**解决方案**：
- 改用mimo-v2.5-pro（纯文本版）
- 或修改RAGFlow源码，移除images参数
