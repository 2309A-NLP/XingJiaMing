### 问题 1：Windows 侧 Docker 未正常连接，无法直接启动容器

**问题现象**

- 在 PowerShell 中执行 `docker version` 时，客户端存在，但无法连接 Docker daemon。
- 报错表现为无法连接 `dockerDesktopLinuxEngine`。

**初步判断**

- 本机并不是没有安装 Docker，而是 Docker 引擎没有实际运行起来。

**排查动作**

- 检查 `docker version`
- 检查 `docker compose version`
- 检查 `wsl -l -v`

**排查结果**

- Docker 客户端和 compose 都已经安装。
- WSL 中的 `Ubuntu` 和 `docker-desktop` 当时处于 `Stopped`。
- 问题根因不是"缺 Docker"，而是"Docker 引擎未启动"。

**处理方法**

- 最终放弃 Windows Docker Desktop 作为主要部署入口。
- 改为使用 `WSL Ubuntu` 中的原生 Docker 环境。

**当前结论**

- 问题已绕开，不再依赖 Windows 侧 Docker Desktop。

### 问题 2：WSL 中 Docker 客户端可用，但 daemon 未启动

**问题现象**

- 在 WSL Ubuntu 中执行 `docker version` 时，客户端存在，但提示：
  - `Cannot connect to the Docker daemon`

**初步判断**

- WSL 中已经安装了原生 Docker，只是服务没有启动。

**排查动作**

- 检查 `which docker`
- 检查 `docker compose version`
- 检查 `systemctl status docker`
- 检查 `/etc/wsl.conf`

**排查结果**

- Ubuntu 中已安装：
  - `docker-ce`
  - `docker-compose-plugin`
  - `containerd`
- `systemd=true`
- `docker.service` 为 `inactive (dead)`，未启动

**处理方法**

- 在 WSL 中执行：

```bash
sudo systemctl start docker
```

**当前结论**

- WSL 中的 Docker 服务已可正常手动启动。

### 问题 4：RAGFlow 已启动，但用户不希望容器自动恢复

**问题现象**

- 默认 compose 配置中多个服务使用了 `restart: unless-stopped`。
- 这意味着用户手动启动 Docker 服务后，容器可能自动恢复运行。
- 用户希望改成"只有手动执行脚本时才启动"。

**初步判断**

- 需要同时处理两层：
  - `docker.service` 是否自启
  - RAGFlow 各容器的重启策略

**排查动作**

- 检查 `systemctl is-enabled docker`
- 检查 compose 文件中的 `restart:` 配置
- 检查当前容器 `RestartPolicy`

**排查结果**

- `docker.service` 在 WSL 中默认不是 enable 状态。
- 但 RAGFlow 相关容器默认是 `restart: unless-stopped`。

**处理方法**

- 新增手动模式覆盖配置：
  - `docker-compose.manual.yml`
- 新增脚本：
  - `start-ragflow-manual.sh`
  - `stop-ragflow-manual.sh`
  - `status-ragflow-manual.sh`
- 将当前容器重启策略调整为 `restart=no`

**当前结论**

- 现在已实现"手动启动模式"。
- 后续只有在手动执行启动脚本时，RAGFlow 才会启动。

### 问题 8：检索测试能命中正确内容，但聊天仍返回"未找到答案"

**问题现象**

- 在知识检索测试中，输入 `P·吉特勒` 或 `发明人` 可以命中正确文本块
- 但在聊天页面中，针对 `CN100342976C.pdf 的发明人是谁？` 仍可能返回 `未找到答案`

**初步判断**

- 问题不是"知识库里没有答案"，而是"聊天链路没有稳定利用已检索到的答案"。

**排查动作**

- 检查聊天参数：相似度阈值、向量/关键词权重、Top N、Rerank
- 检查是否绑定正确知识库
- 查阅源码，对比检索测试与聊天问答两条链路

**排查结果**

- 检索测试与聊天不是同一条实现链路：
  - 检索测试走 `chunk_api.py` 的 `/retrieval`
  - 聊天走 `chat_session.go` 中的 `messagesWithRetrievedKnowledge`
- 聊天链路在 retrieval 后还会执行 `buildKnowledgeBlock`，若为空则返回 `empty_response`

**处理方法**

- 将问题定位从"知识库没有答案"修正为"聊天知识注入/空答案判定有问题"

**当前结论**

- 知识检索测试可命中正确证据
- 聊天链路存在知识注入或空结果判定不稳定现象

### 问题 10：聊天链路的父子分块展开与 Python 老链路存在行为差异

**问题现象**

- 检索测试中可以直接看到命中的 chunk 文本
- 聊天链路中，同样的问题有时会直接返回 `在知识库中未找到您要寻找的答案！`

**排查动作**

- 对比 Go 实现与 Python 老实现
- 检查 Go 版 `RetrievalByChildren` 在父块查找失败时的处理方式

**排查结果**

- Python 老链路在父块缺失时会保留原 child chunk
- Go 链路在父块 `GetChunk` 失败时会直接 `continue`，导致该组 child chunk 被整体丢弃
- 这造成：检索能命中，但聊天因后处理丢块，最终判定"无知识可用"

**处理方法**

- 对 Go 版 `RetrievalByChildren` 做最小修复：父块查找失败时回退保留原 child chunk
- 在聊天链路增加轻量日志

**当前结论**

- 已定位到一个明确的 Go/Python 行为差异点
- 该修复属于保守兼容修复，不改变父块正常展开成功时的主路径行为

### 问题 11：聊天已执行检索，但系统提示词缺少 `{knowledge}`，导致答案无法注入模型

**问题现象**

- 知识检索测试中 `发明人是谁` 已能稳定命中 `［72］发明人 P·吉特勒`
- 但聊天页面连续提问仍返回 `未找到答案`

**排查动作**

- 检查系统提示词内容
- 检查服务端日志中的 embedding、ES 检索、rerank、最终 prompt

**排查结果**

- 后端确实执行了 embedding、ES 检索和 rerank
- 但最终发给模型的 prompt 中没有检索得到的知识文本
- 原因：系统提示词里缺少 `{knowledge}` 占位符

**处理方法**

- 将系统提示词改为显式包含 `{knowledge}`
- 并要求：只能依据知识库内容回答，证据不足再返回 `未找到答案`

**验证结果**

- 加入 `{knowledge}` 后，同类问题重新提问得到正确答案：`P·吉特勒`

**当前结论**

```text
系统提示词中缺少 {knowledge} 占位符，
导致聊天链路虽然执行了检索，但检索结果没有注入给模型，
从而错误地返回"未找到答案"。
```

### 问题 16：RAGFlow API 报错 `images 参数不支持`（2026-06-13 新增）

**问题现象**

```
ERROR: AsyncCompletions.create() got an unexpected keyword argument 'images'
AUTH_ERROR - AsyncCompletions.create() got an unexpected keyword argument 'images'
```
所有 6 个测试题通过 API 调用时全部返回此错误。

**原因分析**

- Dialog 配置的 LLM 是 `mimo-v2.5@MiMo@OpenAI-API-Compatible`
- `mimo-v2.5` 是多模态模型（支持文+图+音）
- RAGFlow 检测到多模态模型后，自动在 OpenAI API 调用中加入 `images` 参数
- 但 MiMo 的 API 端点 `https://token-plan-cn.xiaomimimo.com/v1` 不支持此参数格式

**解决方案**

将 Dialog 的 LLM 从 `mimo-v2.5` 改为 `mimo-v2.5-pro`（纯文本模型）：
```sql
UPDATE dialog SET llm_id='mimo-v2.5-pro@MiMo@OpenAI-API-Compatible' 
WHERE id='043c40e8665611f1ae6bb18953b9dbd1';
```

**备选方案**

1. 修改 RAGFlow 源码 `dialog_service.py`，在调用 LLM 时去掉 `images` 参数
2. 联系 MiMo 官方确认 API 是否支持 images 参数的正确格式
3. 使用其他兼容 OpenAI 格式的纯文本模型（如 DeepSeek）

**影响**

- ✅ 正面：解决了 API 调用失败问题
- ⚠️ 风险：pro 模型无法直接看图回答，依赖预先生成的文字描述 chunk

```python
})
```

**备选方案**

1. 增大 top_n 到 30-50
2. 用多模态 LLM 直接看图回答
3. 调整向量权重，提高关键词匹配的权重

### 问题 19：第 5 题"气流方向"答错（2026-06-13 新增）

**问题现象**

- 问题：`根据文件中第7页图示，气流方向(7)首先经过哪个部件？紧接着会经过哪个部件？`
- 期望：`首先经过台阶形截止面(5)，紧接着经过配气带孔盘(6)`
- 实际：`首先经过管状入口(1)，紧接着经过圆锥形部分(10)`

**原因分析**

- 模型理解了气流的完整路径（从入口开始），但问题问的是箭头(7)标注的位置
- 图片描述 chunk 中没有明确说明箭头(7)的指向

**解决方案**

在图片描述 chunk 末尾追加"关键位置关系和尺寸说明"：
```markdown
### 关键位置关系和尺寸说明
- 气流方向(7)：首先经过台阶形截止面(5)，紧接着经过配气带孔盘(6, 6', 6'')。

```

**备选方案**

1. 在 prompt 中引导模型"关注图中标注的箭头方向"

### 问题 20：prompt_config JSON 编码错误（2026-06-13 新增）

**问题现象**

```
JSONDecodeError('Invalid control character at: line 1 column 242 (char 241)')
```

**原因分析**

- MySQL shell 的多层转义（bash → mysql → JSON）破坏了 JSON 格式
- 中文字符的 Unicode 转义和换行符 `\n` 被错误处理

**解决方案**

用 Python 直接连接 MySQL 更新，避免 shell 转义：
```python
import json, pymysql
config = {"system": "你是工业专利文档问答助手...", ...}
conn = pymysql.connect(host='localhost', port=3306, user='root', 
                       password='infini_rag_flow', db='rag_flow')
cursor = conn.cursor()
cursor.execute("UPDATE dialog SET prompt_config=%s WHERE id=%s", 
               (json.dumps(config), dialog_id))
conn.commit()
```

**备选方案**

1. 通过 RAGFlow 前端页面直接修改 prompt 模板（推荐）
2. 使用 `docker cp` 将 Python 脚本传入容器内执行

### 问题 21：HTTP 代理导致浏览器 502（2026-06-13 新增）

**问题现象**

- 容器内部 `curl localhost:80` 返回 200
- 浏览器访问 `http://localhost` 显示 502 Bad Gateway

**原因分析**

- WSL 环境配置了 HTTP 代理 `http://172.19.112.1:65532`
- 浏览器也走了这个代理，代理无法访问 localhost

**解决方案**

浏览器地址栏直接输入 `http://127.0.0.1`（不是 localhost）

**备选方案**

1. 浏览器代理设置中把 `127.0.0.1` 和 `localhost` 加入排除列表
2. 临时关闭浏览器代理
