# 工单十二 · LightRAG 知识图谱对比系统

> 技术报告 | 2026年6月11日 | RAG + LightRAG 混合架构

---

## 一、项目概述

在传统 RAG（向量检索 + BM25）基础上，引入 **LightRAG 知识图谱**，实现两路检索对比与融合回答。

### 核心功能
- 传统 RAG 流式回答（~3秒响应）
- LightRAG 知识图谱检索（后台并行）
- 两路结果智能融合
- RAG vs LightRAG 对比弹窗（左边传统RAG，右边LightRAG流式输出）
- 准确率对比分析（LLM-as-Judge）
- RAGAS 框架评测

---

## 二、技术栈

| 技术 | 用途 | 说明 |
|------|------|------|
| **LightRAG** | 知识图谱构建与检索 | HKUDS/LightRAG 库，NetworkX 图存储 |
| **NanoVectorDB** | LightRAG 内部向量存储 | 实体/关系/文档片段的向量索引 |
| **Milvus** | 传统 RAG 向量存储 | rag_workorder12 collection，1315 条 |
| **BGE-M3** | Embedding 模型 | 1024 维，GPU 加速 |
| **BGE-Reranker** | 重排序模型 | 传统 RAG 用，LightRAG 已关闭 |
| **DeepSeek** | LLM 生成 | deepseek-chat，流式输出 |
| **SSE** | 流式通信 | 前后端实时 token 传输 |
| **NetworkX** | 图存储 | LightRAG 默认图存储（替代 Neo4j） |

---

## 三、系统架构

```
用户提问
  ├──→ 传统RAG（2-3秒）──────→ 立即展示回答
  │      ├── 向量检索 (Milvus + BGE-M3)
  │      ├── BM25 全文检索
  │      ├── RRF 融合 + BGE-Rerank
  │      └── DeepSeek 流式生成
  │
  └──→ LightRAG（后台并行，3-5秒）
         ├── 知识图谱检索 (NetworkX)
         │    ├── 实体匹配 (top_k=5)
         │    ├── 关系遍历 (top_k=5)
         │    └── 文档片段 (chunk_top_k=3)
         └── DeepSeek 流式生成（aquery_data + 独立LLM调用）
              │
              └──→ 融合引擎（DeepSeek 流式）→ 主回答更新为混合版本
```

### 关键设计决策

**aquery_data 解耦架构：** LightRAG 的 `aquery()` 方法内部会调用 LLM 生成回答，无法流式输出。改用 `aquery_data()` 只做图谱检索（返回 entities/relations/chunks），然后用独立的 DeepSeek 流式 API 生成回答。这样既保留了图谱检索能力，又实现了流式输出。

## 四、实现过程与遇到的阻碍

### 阻碍 1：Milvus Collection 配置错误

**现象：** 后端查询返回的数据来自工单六，不是工单十二

**原因：** `.env` 中 `MILVUS_COLLECTION=rag_workorder6`，应该是 `rag_workorder12`

**修复：** 改 `.env` 配置 + 从 rag_workorder6 迁移 1315 条数据到 rag_workorder12

---

### 阻顾 2：LightRAG 文档插入反复超时失败

**现象：** 559 个 chunks 的文档插入到一半就失败，error: `Request timed out`

**原因：** DeepSeek API 偶尔网络抖动，但 OpenAI SDK 没设 timeout 和 max_retries，一次超时整任务报废

**修复：**
```python
client = AsyncOpenAI(api_key=api_key, base_url=base_url, timeout=120.0, max_retries=3)
```
同时手动清理 `kv_store_doc_status.json` 中的 processing 状态，重新插入

---

### 阻碍 3：LightRAG 查询耗时 70 秒

**现象：** 一次 LightRAG 查询需要 70 秒，用户无法接受

**原因：**
- top_k=10 检索了 299 个关系、87 个 chunks
- Rerank 用 CrossEncoder 对 71 个 chunks 打分，GPU 跑了 50 秒

**优化：**
```python
param = QueryParam(
    mode="hybrid",
    top_k=5,           # 10 → 5，减少实体/关系
    chunk_top_k=3,      # 5 → 3，减少文档片段
    enable_rerank=False  # 关闭 Rerank（图谱本身已有权重排序）
)
```

**效果：** 70 秒 → 1.8 秒（提速 38 倍）

---

### 阻碍 4：对比弹窗 LightRAG 重新查询

**现象：** 点击"RAG vs LightRAG 对比"按钮，LightRAG 又花了 168 秒重新查询

**原因：** 主回答流程已拿到 LightRAG 结果，但没存到消息里，对比按钮重新发起查询

**修复：** 收到 LightRAG 结果时**立即存储**到消息状态，对比按钮通过 `useEffect` 同步，直接复用预存结果

---

### 阻碍 5：前端 node_modules 平台冲突

**现象：** WSL 装的 npm 包（Linux 二进制）在 Windows 侧运行报错 `MODULE_NOT_FOUND`

**原因：** rollup 等包有平台原生模块，WSL 和 Windows 不兼容

**修复：** 用 `cmd.exe /c npm install --include=dev` 从 Windows 侧重装

---

### 阻碍 6：start.bat 双击没反应

**现象：** 双击 start.bat 无任何窗口弹出

**原因：** bat 文件中 WSL 命令的引号嵌套 + 中文路径编码问题

**修复：** 把 WSL 命令拆到 `start_wsl.sh`，bat 只负责调用脚本 + 启动前端

---

### 阻碍 7：RAGAS 与 DeepSeek API 不兼容

**现象：** RAGAS 默认用 `gpt-4o-mini`，发送 `n>1` 参数，DeepSeek/MiMo API 不支持

**修复：** 手写 RAGAS 评测逻辑（LLM-as-Judge），用 DeepSeek 直接评分

## 六、RAGAS 评测（DeepSeek LLM-as-Judge）

| 指标 | 传统RAG | LightRAG | 胜出 |
|------|---------|----------|------|
| **Faithfulness** | 0.15 | **1.00** | LightRAG |
| **Answer Relevancy** | 1.00 | 1.00 | 平局 |
| **Context Precision** | 0.40 | **0.53** | LightRAG |
| **Context Recall** | 0.22 | **0.49** | LightRAG |

### RAGAS 结果分析

**传统RAG Faithfulness 低的原因（0.15）：**

传统RAG把**两个招股书的内容混在一起**了。问的是力源信息（招股书2），但检索到了兴图新科（招股书1）的内容来回答。向量检索只看语义相似度，不区分文档来源，导致跨文档混淆。

**LightRAG Faithfulness 高的原因（1.00）：**

知识图谱通过实体关联（如"力源信息"→"IC市场"→"汽车电子"），能更精确地区分不同文档的内容。检索到的上下文和回答高度一致。

**结论：LightRAG 在多文档场景下比传统RAG更可靠。**

## 七、最佳实践建议

### 什么时候用传统RAG？
- 📊 精确数值查询（财务数据、增长率、百分比）
- 📋 表格数据提取
- ⏱️ 需要快速响应的场景（<3秒）

### 什么时候用LightRAG？
- 🔗 跨文档实体关系推理（"A公司的供应商B的客户C是谁？"）
- 📊 多维度总结归纳（"这家公司面临哪些风险？"）
- 🕸️ 需要关联分析的复杂问题

### 混合方案（当前实现）
先用传统RAG保证3秒响应，后台并行跑LightRAG，融合两路结果。用户感知秒回，答案质量更高。

| 优化项 | 优化前 | 优化后 | 提升 |
|--------|--------|--------|------|
| LightRAG 查询时间 | 70s | 1.8s | **38倍** |

### 参数调优记录

| 参数 | 初始值 | 优化值 | 原因 |
|------|--------|--------|------|
| top_k | 10 | 5 | 减少实体/关系检索量 |
| chunk_top_k | 5 | 3 | 减少文档片段 |
| enable_rerank | True | False | Rerank 71 chunks 花 50s，图谱自身排序够用 |
| API timeout | 30s | 120s | 防止网络抖动导致任务失败 |
| max_retries | 0 | 3 | 自动重试，不因单次超时报废 |

## 九、已知限制与后续优化

1. **LightRAG 实体混淆**：Q1 中"IC卡"被误答为"工业控制"，图谱推理时相似实体易混淆
2. **两文档混合**：传统RAG 检索时不区分文档来源，需要在 chunk 元数据中加文档标识
3. **融合延迟**：用户先看到传统RAG回答，约10秒后更新为融合版本，体验可以优化为渐进式
4. **Neo4j 未启用**：当前用 NetworkX 内存图，切换到 Neo4j 可支持更大规模知识图谱
