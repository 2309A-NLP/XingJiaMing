## 2. 关键问题排查记录

### 2.1 Milvus 不是“没起”，而是客户端接口不兼容

现象：

- 初始启动阶段在 `vector_store.create()` 报错。
- 报错指向 `MilvusClient.prepare_index_params()` / `create_collection()` 调用方式不匹配。

排查结论：

- Milvus 容器在 WSL Docker 中正常运行。
- `127.0.0.1:19530` 连通。
- 根因是 `工单十三` 的代码写法和当前 `pymilvus 2.3.4` 客户端 API 不兼容。

处理动作：

- 修复建表逻辑。
- 修复 `count()` 统计逻辑。
- 修复 `delete_by_source()` 的删除参数。
- 补充回归测试，防止再次回退。

### 2.2 Redis 可连通，但启用了密码

现象：

- 启动时短期记忆报 `Authentication required`。

排查结论：

- Redis 容器正常运行。
- 当前容器以 `--requirepass infini_rag_flow` 启动。

处理动作：

- `SessionMemory` 改为读取：
  - `REDIS_HOST`
  - `REDIS_PORT`
  - `REDIS_PASSWORD`
  - `REDIS_DB`
- `.env` 已补充 Redis 密码配置。

### 2.3 当前运行环境是 CPU 版 torch，不是没有 GPU

排查结论：

- 机器存在可用 GPU：`NVIDIA GeForce RTX 4060`
- 但 `工单十三/.venv` 中安装的是 `torch 2.12.0+cpu`
- 因此 `torch.cuda.is_available()` 为 `False`

影响：

- embedding / rerank 均在 CPU 上运行
- 冷启动与重排阶段耗时偏高

### 2.4 首次未达标的真正瓶颈是 rerank，不是向量检索

现象：

- 第一轮 benchmark 出现 `p95 = 3518ms`
- 只有“注册资本是多少”这一类问题明显拖尾

拆解结果：

- `embedding` 大约 `150ms - 180ms`
- `vector_search` 大约 `220ms - 360ms`
- `rerank` 大约 `2500ms - 3100ms`

结论：

- 慢尾来自 CPU 下的 BGE rerank 候选池过大。

处理动作：

- 为 CPU 场景单独引入更小的 rerank 候选池。
- 保留 GPU 配置能力，不影响后续继续升级。

## 3. 关键优化结果

### 优化前

- `avg_total_ms = 1226.8`
- `p50_total_ms = 507`
- `p95_total_ms = 3518`
- `p99_total_ms = 4103`
- `under_3s_rate = 0.75`

### 优化后

- `avg_total_ms = 811.2`
- `p50_total_ms = 499`
- `p95_total_ms = 1933`
- `p99_total_ms = 2185`
- `under_3s_rate = 1.0`

## 4. 代码层关键改动摘要

- 新增 `POST /api/query/retrieve`
- 补齐统一性能字段：
  - `trace_id`
  - `timings`
  - `retrieval_time_ms`
  - `total_time_ms`
  - `cache_hit`
- `Milvus VectorStore` 兼容当前客户端版本
- `SessionMemory` 支持 Redis 密码认证
- `BGEReranker` 修复无 CUDA 时的 CPU 回退设备标记
- `Retriever` 在 CPU 场景下收紧 rerank 候选池
